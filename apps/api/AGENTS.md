# C-Ride Backend Agent Context

Use a NestJS modular monolith organized by business domain.

- Bounded contexts: `identity`, `drivers`, `rides`, `notifications`. Add the `drivers` context when implementing driver registration/onboarding; it owns `DriverProfile` and `Vehicle`, not the `DRIVER` role itself.
- `RIDER` and `DRIVER` are roles/actors, not separate top-level backend modules.
- Root `infrastructure` is technology-specific and business-agnostic.
- Domain-specific adapters belong inside the owning module.
- Configuration must flow through the config layer.
- Do not add authentication, ride, WebSocket, job, notification, or persistence business logic during scaffolding.
- Don't ever make changes to prisma migrations. Migrations are generated by the Prisma CLI and should be treated as a source of truth.

## Layer Responsibilities

- Each context uses `domain/{entities,enums,repositories}`, `application/use-cases`, `infrastructure`, `presentation`, and a root `<context>.module.ts`. Add subdirectories only when needed.
- Domain entities and policies own invariants and lifecycle transitions. Domain code must not depend on NestJS, Prisma, HTTP DTOs, Redis, queues, JWT libraries, or Firebase.
- Application use cases orchestrate domain behavior through abstract repository and capability contracts. Put non-repository contracts in `application/contracts`; repositories always belong in `domain/repositories`. Application code must not depend on concrete adapters, generated Prisma types, HTTP request objects, or transport exceptions.
- Infrastructure implements persistence, hashing, token, cache, queue, and delivery contracts. Keep Prisma queries, transactions, generated types, and persistence mappers here. Never expose Prisma transaction clients through application/domain contracts.
- Presentation owns controllers, gateways, request/response DTOs, guards, decorators, validation, and transport error mapping. Controllers and gateways call use cases; they do not implement business rules or query Prisma.
- Use named operations such as `RegisterUserUseCase`, `OnboardDriverVehicleUseCase`, and `AcceptRideUseCase`; do not introduce generic `UsersService`, `DriversService`, or `RidesService` orchestration classes.
- Root `infrastructure` provides business-agnostic clients; context-specific adapters stay in the context. Use `common` for transport utilities and `shared` only for genuinely shared, framework-independent types/utilities.

## Abstract Class Providers

- Define injectable repository contracts as exported abstract classes, for example `export abstract class UserRepository { abstract findById(id: string): Promise<User | null>; }`.
- Bind `{ provide: UserRepository, useClass: PrismaUserRepository }` in the owning module and inject `UserRepository` directly. Adapters may implement the abstract class when no base behavior is needed.
- Do not replace these contracts with interfaces plus string/Symbol tokens. Use abstract classes for other injected capability contracts as well; plain interfaces/types are suitable for data-only shapes.
- Export only contracts or application entry points needed by consumers. Cross-context callers use public application contracts, not another context's persistence adapter or private repositories.
- For atomic cross-context workflows, define a framework-independent application contract and implement the transaction in infrastructure. Document ownership and coordinate context-owned persistence adapters without circular module dependencies.
- Return explicit safe response objects; never serialize domain entities containing credentials directly.

## Required End-of-Cycle Review

- Review every module, class, and function created or modified in the cycle and all affected callers/dependencies for adherence to the rules above. Inspect module imports, exports, DI bindings, use-case responsibilities, mappers, domain rules, authorization, transaction boundaries, and error paths.
- Run relevant checks and focused tests; verify runtime DI composition when provider wiring changes. Report passed checks separately from unverified database, queue, socket, or external-provider behavior.
- Update `specs/implementation.md` only on evidence of completion. Preserve unrelated work and completed checklist history; add explicit follow-up tasks when existing behavior needs further verification.

## Project and Infrastructure

- Stack: NestJS, strict TypeScript, PostgreSQL/Prisma, Redis, BullMQ, Socket.IO, Firebase Admin, OpenTelemetry, and Argon2id through the `argon2` package.
- Prefer current stable packages when adding dependencies; avoid prereleases unless requested and do not upgrade unrelated dependencies.
- Source roots are `config`, `common`, `infrastructure`, `modules`, and `shared`.
- Reuse root infrastructure: `database/database.module.ts` and `prisma.service.ts`, `cache/cache.module.ts` and `redis.service.ts`, `queue/queue.module.ts`, `firebase/firebase.module.ts` and `firebase.service.ts`, and `telemetry/telemetry.module.ts`.
- Root clients expose generic technology operations such as Redis get/set; ride-specific cache operations belong in rides infrastructure.
- PostgreSQL is the durable source of truth. Redis holds cached/temporary data and WebSockets communicate changes.
- Use BullMQ for asynchronous notifications. Keep Firebase SDK behavior separate from ride business logic.
- Read configuration through the configuration layer, not scattered `process.env` calls.
- Keep rider and driver ride operations in the same rides context, organized as named use cases rather than separate actor modules.
- Avoid generic `BaseRepository<T>` patterns and abstractions without a demonstrated need; prefer domain-oriented repository operations.
- Do not introduce microservices, Kafka, Kubernetes, event sourcing, CQRS infrastructure, or speculative domains such as payments/pricing unless requested.

## Phase Scope

Keep implementation scoped to the requested phase. During initial scaffolding, create only structure, module/infrastructure skeletons, configuration, dependencies, Prisma initialization, Docker Compose, and environment files. Implement business workflows only when the requested phase authorizes them.
